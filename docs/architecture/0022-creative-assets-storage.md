# ADR 0022: versioned creative assets and private object-storage boundary

Date: 2026-10-08. Status: implemented for review under #225; not deployed.
Predecessors: RECONCILIATION.md §§1.8–1.9/3, MASTER_PLAN.md storage rules.

## Decision and scope

An edited image is a version graph, not a set of uploads.
`creative_assets` carries stable identity (organization, capability,
title, originating job); `creative_asset_versions` carries one immutable
row per output (version sequence, parent link, producing job, MIME,
dimensions, bytes, sha256, object key, thumbnail key, provenance,
prompt/template references, method, review state). Edits create new
versions; a trigger permits only review-state transitions on history
rows, and deletes are forbidden. Human approval moves a version
`draft/in_review → approved/rejected` with reviewer identity and
mandatory rejection feedback; re-decision of terminal versions is
rejected so approvals cannot be replayed into a different outcome.

Generated bytes never enter PostgreSQL. The database stores metadata
and object references only. Object keys are tenant-scoped and immutable
(`t/<org>/<capability>/<asset>/v<version>.<ext>`), checksums are
verified on write, previews are short-lived signed hints (never the
canonical identity), and deletion/retention is an explicit audited
workflow. P1a ships the abstraction plus an in-memory test adapter;
production backend selection (S3-compatible) stays a later decision
with license/cost review. No public-by-default bucket is ever acceptable.

## Non-goals of this decision

No production bucket, credential, CDN, thumbnail pipeline, or lifecycle
policy beyond the interface. Product-fidelity inspection (logo, package
text, shape, color) arrives with the Product Studio slice, reusing this
version graph as its evidence base.
