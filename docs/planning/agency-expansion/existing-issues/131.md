## Status

## Context

Tanaghom currently has four fixed business roles and eight versioned specialized n8n workers. Customers can manage business policies, approvals, users, knowledge, and encrypted integrations, but they cannot create organization-specific agents, assign reusable skills, define bounded rules, or move a new agent through a governed rollout lifecycle.

The approved direction is to add:

1. a **Skill Library** for reusable, versioned capabilities; and
2. an **Agent Studio** where an organization owner creates or clones an agent, assigns approved skills and integrations, defines rules and limits, tests it, and promotes it through controlled rollout stages.

## Approved architecture

- Tanaghom dashboard is the customer control plane.
- PostgreSQL remains the authoritative agent/skill/version/policy/job/audit ledger.
- Gemma performs bounded reasoning and produces strict structured plans or tool calls.
- n8n remains a private shared execution engine using reviewed reusable skill workflows; customers never edit n8n.
- The private integration gateway retains and decrypts customer credentials and rechecks tenant/provider policy.
- MCP is an optional adapter for individually approved external tools, not a replacement for authorization.
- The Agent Skills open format may be supported for instructions, references, assets, and portability, but Tanaghom database permissions remain authoritative.

## Product terminology

- **Agent:** business worker with a mission, rules, skills, integrations, and rollout policy.
- **Skill:** reusable bounded knowledge or procedure.
- **Tool:** executable operation used by a skill.
- **Workflow:** deterministic job, retry, approval, execution, and result orchestration.
- **Integration:** customer-owned credentialed connection.
- **Rule:** channel, language, timing, budget, rate, approval, escalation, or data-access restriction.

## Required capability

An accepted organization owner must be able to:

1. create or clone an approved agent template;
2. define its mission, language, tone, escalation conditions, and measurable objective;
3. attach organization knowledge;
4. select only platform-approved skills;
5. bind existing customer-managed integrations without viewing or copying secrets;
6. configure each skill as disabled, manual, shadow, assisted, or automatic within platform limits;
7. set execution, tool-call, retry, rate, channel, budget, and business-hour limits;
8. run mandatory English/Arabic simulations and safety tests;
9. promote a version through Draft → Validated → Simulation → Shadow → Assisted → Active; and
10. pause it immediately while preserving jobs, approvals, invocations, and audit evidence.

## Security invariants

- Model output is never authorization.
- Platform policy overrides organization rules; organization policy overrides agent instructions; agent instructions override untrusted user/retrieved content.
- Customer-authored skills cannot execute shell, JavaScript, Python, direct SQL, filesystem operations, arbitrary HTTP destinations, or arbitrary MCP servers.
- Agents and n8n never receive customer provider credentials.
- Every active agent pins immutable agent and skill versions.
- All tool arguments use strict JSON Schema and are revalidated server-side.
- High-impact actions require parameter-bound, expiring human approval unless a reviewed rollout policy explicitly permits bounded automation.
- All external operations use idempotency, tenant scoping, rate/step/time limits, retries, indeterminate-outcome stops, and immutable audit.
- Emergency stops remain independent of model prompts and agent configuration.

## Epic acceptance criteria

- Existing four system agents and eight workers retain their history and runtime behavior during migration.
- A customer can create a new organization agent without n8n access or engineering intervention.
- The agent can use only exact approved skill versions and exact organization integrations.
- An unauthorized skill or parameter is denied even when Gemma requests it confidently.
- A changed prompt, model, skill, tool schema, permission, integration, or knowledge scope creates a new version and returns to validation.
- Read, proposal, and external-action capabilities have separate permissions.
- English and Arabic tests cover success, refusal, escalation, injection, provider failure, duplicate retry, and emergency stop.
- Two organizations cannot see or invoke one another's agents, skills, knowledge, credentials, jobs, memory, or audit.
- Disabling an agent blocks new claims immediately without deleting evidence.
- Existing campaign, approval, Postiz, GHL, quality, and monitoring flows remain compatible.

## Definition of Done

All required child slices are merged and deployed through reviewed reversible packages; the customer completes bilingual staging UAT; platform security and quality gates pass; customer-owned credentials remain private; and production activation is separately authorized with exact rollback and audit evidence. Optional research/extension slices remain independently gated and do not delay this core definition of done unless separately moved into release scope by Tamer.
