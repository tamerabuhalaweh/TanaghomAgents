## Problem

Creating an agent or skill is not sufficient evidence that it is safe, useful, tenant-isolated, or production-ready. Any material change to prompts, skills, tools, schemas, knowledge, integrations, permissions, model/runtime, or rollout policy must pass repeatable certification before autonomy expands.

## Objective

Build the mandatory evaluation, evidence, approval, and rollout gate for organization agents and skill versions, covering functional quality, Arabic/English behavior, security abuse cases, provider resilience, human oversight, and controlled production promotion.

## Required evaluation layers

1. **Static validation** — schemas, permissions, references, hashes, limits, compatibility, secrets, unsafe content.
2. **Contract tests** — exact input/output and controlled executor behavior.
3. **Simulation** — disposable PostgreSQL/n8n, simulated Gemma/provider/gateway, no credentials.
4. **Adversarial tests** — direct/indirect prompt injection, unauthorized tool request, cross-tenant access, memory poisoning, data exfiltration, approval manipulation, excessive steps/cost, malicious tool output, and agent-to-agent privilege escalation.
5. **Bilingual quality** — English and Arabic intent, grounding, tone, refusal, escalation, tool selection, and RTL evidence.
6. **Staging shadow** — customer-shaped events with zero external action.
7. **Assisted UAT** — staging accounts, explicit approvals, allowlisted channels/contacts, duplicate/retry and indeterminate-operation tests.
8. **Bounded canary** — minimum volume, duration, metrics, stop conditions, and rollback.
9. **Production approval** — separate owner/platform authorization after evidence review.

## Required evidence

- Exact agent, skill, model, tool, schema, prompt, knowledge, and executor versions/hashes.
- Test dataset provenance and de-identification evidence.
- Expected versus actual structured outputs.
- Tool requests, authorization/refusal reasons, approvals, and sanitized results.
- Quality, groundedness, escalation, safety, latency, retry, duplicate, conversion, and cost metrics.
- Emergency-stop and rollback proof.
- Reviewer identity, decision, timestamp, expiry, and conditions.
- No secrets or prohibited PII in evidence/logs.

## Promotion rules

- A version cannot skip stages.
- Failed or stale evidence blocks promotion.
- Changed prompts, skills, tools, permissions, schemas, knowledge scope, integrations, model/parser, or platform maximums invalidate affected evidence.
- High-risk skills cannot become automatic until platform certification and minimum organization evidence pass.
- Customer owner controls business rollout; platform operator controls runtime certification and maximum autonomy.
- Emergency stop and rollback remain available at every stage.

## Acceptance criteria

- Mandatory suites include successful, refusal, escalation, timeout, rate-limit, malformed response, provider uncertainty, duplicate delivery, dependency loss, and recovery cases.
- Unauthorized tools are denied even when the model requests them confidently.
- Exact parameter-bound approval cannot be reused for different parameters, agents, skills, organizations, or after expiry.
- A malicious knowledge document, inbound message, MCP description/output, or prior memory cannot grant authority or leak credentials/context.
- English and Arabic scenarios meet separately reported acceptance thresholds; aggregate scores cannot hide a language failure.
- Shadow mode produces no external operation; assisted mode performs only exact approved allowlisted actions.
- Pausing/emergency stop blocks new claims and preserves in-flight/historical evidence.
- Tenancy, idempotency, backpressure, retention, monitoring, notification, and rollback tests pass.
- The dashboard gives the customer a clear GO/NO-GO report and exact blockers.

## Definition of Done

The evaluation registry, scenario builder, immutable evidence model, mandatory platform suites, organization UAT workflow, metrics dashboard, promotion state machine, expiry/invalidation rules, monitoring, runbooks, and reversible deployment package are reviewed and merged. At least one English/Arabic staging agent completes Draft → Shadow → Assisted acceptance with no unauthorized action. Production activation remains a separate explicit decision.
