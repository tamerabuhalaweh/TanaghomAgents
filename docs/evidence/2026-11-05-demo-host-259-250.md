## Defects the execution exposed (all fixed on the branch)

1. `verify_backup` piped `pg_restore` into `grep -q`; SIGPIPE under `pipefail`
   reported a valid dump as having no table data, so upgrade refused a backup
   that backup had just verified.
2. The drift allowlist expected `table=44->45` while `count_delta_report` prints
   `table 44->45`, so every correct upgrade was refused as drift.
3. The allowlist then read the pre-upgrade ledger count after migrating.
4. `pg_restore --clean` cannot `DROP SCHEMA tanaghom` once a newer migration owns
   a function in it.
5. The dump already contains `CREATE SCHEMA public`, so the restore pre-step's
   copy aborted the restore.
6. Restore ended with a bare `compose up -d`, which pulled in `migrate` and
   silently advanced a restored 0047 database to 0048 before any deliberate
   upgrade. It now returns the application with `--no-deps`.
7. `rm -rf /data/*` leaves dotfiles, so a runtime marker in the object volume
   survived and made the restored inventory 18 against 17.
8. The dump does not recreate `pgcrypto` (installed by migration 0030), so after
   a restore `agent_runtime_sha256` failed with `42883` and every workspace write
   returned 503. The extension is now ensured after the dump.
